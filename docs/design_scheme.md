# 设计方案

## 文档定位

- 说明这次课程实验要做成什么样子
- 说明学生需要完成的工作，以及我们提供的代码、工具和教学材料
- 记录设计原则、功能边界和已经做出的取舍
- 列出课程准备工作和最终交付产物
- 尚未确定的问题单独列出，后续通过参考实现和试做调整

## 学生基础与实验约束
- 认为所有人都只是学习过操作系统的概念性知识，无任何操作系统开发相关的经验或知识
- 认为所有人都能力边界都符合如下几条约束：

### 可以假定学生掌握的内容
- 已经学习过操作系统课程，了解进程、内存、文件和用户态、内核态等基本概念。
- 会编写 C 语言程序。
- 能按照指导修改代码、复制命令、运行程序和查看输出。

### 不能假定学生掌握的内容
- Linux 终端、Git、Makefile 和交叉编译工具链。
- QEMU、GDB、readelf、objdump、nm 等工具。
- 入口汇编、链接器脚本、可执行文件的加载和内存布局。
- RISC-V 指令、CSR、陷阱入口和特权级切换的具体实现。
- 编码智能体；教学支持不能依赖学生会使用 Codex、Claude Code 或 Cursor。

## 设计原则
### 可完成性约束
- 必须让符合上文描述能力边界的学生可以完成除附加题以外的实验
- 预期工作量都必须只考虑古法编程的情况（即不借助任何AI工具进行编码工作），要让纯手写的人可以无压力的完成实验

### 学生主要实现操作系统功能
- 不能让学生需要去学习与操作系统内核无关的，仅会用到一次的知识
- 不让一次性的工程配置占用主要实验时间。
- 必须接触的底层知识由指导书解释，不要求学生自行查齐所有资料。
- 提供启动、构建、调试和测试所需的代码，不提供需要学生实现的内核功能
- 不指定学生的内核目录结构、内部数据结构和具体算法，除非测试兼容性确实需要。
- 所有测试程序，只定义要被验收的接口格式和语义，不定义内核的结构
### 每个模块都能独立开始
- （当跟随实验指导书完成前置实验后）学生不需要先完成其他模块，就能开发和测试当前模块。
- 模块独立验收，完整内核另做集成验收。
- 教学讲解可以按顺序展开，不把讲解顺序变成学生必须遵守的开发顺序。
- 尽可能保证任务的独立性和可并行性，只在必要的时候做线性的任务安排

### 要求必须能够被测试
- 每项必做功能都提供容易运行的测试。
- 测试只检查API/ABI的行为，不检查学生是否采用指定内部实现。
- 同时测试正常行为、边界输入和失败后的状态。
- 不用未公开的功能要求扣分。
- 测试失败应帮助学生定位问题，不能只输出一个 FAIL。


### 时间与工作量
- 按两周安排，给阅读、调试和其他课程留出时间。
- 按单个学生独立完成设计，不依赖多人分工。
- 学生实现代码预计约 3000 至 4000 行。
- 实际编码时间预计不超过 48 小时，另外估算阅读、调试和集成时间。
- 行数和时间先作为预算，通过参考实现和试做验证，不作为评分指标。

### 评价不能增加无关负担
- 所有评分标准都不能惩罚认真做事的学生，哪怕会漏掉直接完全通过 AI 工具完成实验或者抄袭别人的代码的学生
- 集成单独评价。
- 不以代码行数、实现速度或 AI 检测结果判断成绩。
- 不阻止学生使用 AI 工具。
- 不为防止少数学生完全依赖 AI，给认真完成实验的学生增加大量额外工作。

## 课设目标

### 学生最终完成的系统
- 基于 QEMU RISC-V 64平台运行。
- 使用自定义 ABI，不考虑兼容 Linux ABI。
- 支持必做范围内的用户程序、内存管理、任务调度和文件操作。
- 能通过模块测试和完整用户程序测试。

### 基础部分

- 内核启动后进入 shell。
- shell 启动提供的文本编辑器。
- 编辑器创建或修改文件并保存。
- ls 显示文件。
- cat 显示写入内容。
- rm 删除文件。
- 说明上述应用由我们提供和适配，学生不需要编写 shell 或编辑器。
- 明确文件修改是否只要求在本次运行期间保留。

### 附加部分的最终运行场景
- 接入提供的 Virtio-GPU 和 Virtio-Input 驱动。
- 运行提供的精简 mGBA。
- 加载指定 ROM，显示画面并响应操作。
- 不要求声音和下次启动后的存档恢复。
- 附加部分不影响基础实验的完成和验收。

### 要达到的教学目标

我们要引导学生经历从零开发操作系统内核的过程，从最开始的成功运行裸机程序，通过串口输入输出，上下文保存和切换，trap_handler，CPU特权级切换，在无页表保护下运行第一个用户态指令流，测试简单的 console_print 系统调用，再到文件系统读写，从elf加载用户程序，再通过时间片轮转并发运行多道用户程序，再到逐步去完善各个模块的功能以及实现

## 设计思路

我们在进行任务制定时使用目标导向的思路，从被移植的用户程序需要哪些最简单的系统调用开始，通过这些系统调用去定义学生需要支持哪些系统调用，以及定义该系统调用依赖的操作系统内核子模块需要具备哪些功能

## 一些重要问题的决定

### 定义“从零开始”

一句话：学生在可启动、可调试的工程中，自行设计并实现操作系统核心功能。

具体而言，我们给学生提供一个配置好 Makefile，交叉编译工具链以及基本脚本（包含qemu启动，gdb的server和client启动的脚本）的项目基本框架，且提前编写好start.S，让学生可以直接进入自己熟悉的开发环境，而不是先折腾启动代码怎么写，入口函数放在什么地址这种事情。即，从零开始是指内核从零开始，真正的入口是可以运行的裸机程序和包装好的命令。
